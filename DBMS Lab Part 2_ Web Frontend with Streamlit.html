Why Streamlit?

Normal web development needs HTML, CSS, JavaScript and a server framework before anything works. Streamlit skips all of that. Students write a normal Python script, and each Python line such as st.text_input(...) becomes a web widget. It also displays tables and charts directly from data, which suits a database course.

Charts Needs extra libraries st.bar_chart(df)

Setup

  1. Work in the same student_lab folder from Part 1. It must already contain db_config.py and a working students table.
  2. Install the libraries: pip install streamlit pandas
  3. Create db.py. It holds the one database helper that every web page will import:
import psycopg2
from db_config import DB_SETTINGS

def run(sql, params=(), fetch=False):
    """Connect, run one statement, commit, close. Returns rows if fetch=True."""
    conn = psycopg2.connect(**DB_SETTINGS)
    try:
        cur = conn.cursor()
        cur.execute(sql, params)
        rows = cur.fetchall() if fetch else None
        conn.commit()
        return rows
    except Exception:
        conn.rollback()
        raise
    finally:
        conn.close()

This is the same run() function from the Part 1 desktop app. Pulling it into its own file means Tkinter, Streamlit or any later project can import it.

The one idea to understand first

A Streamlit script runs from top to bottom every time the user clicks or types something. Widgets are just function calls that return the current value. A button returns True only during the run caused by its click.

  • You do not write event handlers or command= callbacks like in Tkinter.
  • Order matters. If you show a table before the code that inserts a row, the table shows old data. Run the database change first, then read and display.
  • To save a file and see the effect, click Always rerun in the top-right corner of the page.

Step 4Add a student with a form

Create web_step4.py. A st.form waits until the user presses the submit button, so the script does not rerun on every keystroke. The insert code sits before the table, so the table already includes the new row.

import pandas as pd
import streamlit as st
from db import run

st.title("Student Records")

with st.form("add_form", clear_on_submit=True):
    name = st.text_input("Name")
    branch = st.selectbox("Branch", ["CSE", "ECE", "EEE", "MECH", "CIVIL"])
    marks = st.number_input("Marks", min_value=0, max_value=100, step=1)
    submitted = st.form_submit_button("Add student")

if submitted:
    if not name.strip():
        st.error("Name is required.")
    else:
        run("INSERT INTO students (name, branch, marks) VALUES (%s, %s, %s)",
            (name.strip(), branch, int(marks)))
        st.success("Added " + name.strip())

rows = run("SELECT id, name, branch, marks FROM students ORDER BY id", fetch=True)
st.dataframe(pd.DataFrame(rows, columns=["ID", "Name", "Branch", "Marks"]), hide_index=True)

Still true from Part 1: use %s placeholders, never f-strings, so user input cannot inject SQL.

Step 5The full app: view, search, add, edit, delete

Save as web_app.py and run streamlit run web_app.py. It has summary numbers, a chart, and three tabs.

import pandas as pd
import streamlit as st
from db import run

BRANCHES = ["CSE", "ECE", "EEE", "MECH", "CIVIL"]

st.set_page_config(page_title="Student Records", page_icon="🎓", layout="wide")
st.title("🎓 Student Records")

# Show a message that was saved before the page reran
if "flash" in st.session_state:
    st.success(st.session_state.pop("flash"))

def load(search=""):
    rows = run("SELECT id, name, branch, marks FROM students "
               "WHERE name ILIKE %s ORDER BY id", ("%" + search + "%",), fetch=True)
    return pd.DataFrame(rows, columns=["id", "name", "branch", "marks"])

def done(message):
    """Remember a message, then rerun so every table shows fresh data."""
    st.session_state["flash"] = message
    st.rerun()

all_df = load()

c1, c2, c3 = st.columns(3)
c1.metric("Students", len(all_df))
c2.metric("Average marks", round(all_df["marks"].mean(), 1) if len(all_df) else 0)
c3.metric("Highest marks", int(all_df["marks"].max()) if len(all_df) else 0)

tab_view, tab_add, tab_edit = st.tabs(["View", "Add student", "Edit or delete"])

with tab_view:
    search = st.text_input("Search by name", key="search")
    st.dataframe(load(search), hide_index=True)
    if len(all_df):
        st.subheader("Average marks by branch")
        st.bar_chart(all_df.groupby("branch")["marks"].mean())

with tab_add:
    with st.form("add_form", clear_on_submit=True):
        new_name = st.text_input("Name", key="add_name")
        new_branch = st.selectbox("Branch", BRANCHES, key="add_branch")
        new_marks = st.number_input("Marks", 0, 100, key="add_marks")
        add_clicked = st.form_submit_button("Add student")
    if add_clicked:
        if not new_name.strip():
            st.error("Name is required.")
        else:
            run("INSERT INTO students (name, branch, marks) VALUES (%s, %s, %s)",
                (new_name.strip(), new_branch, int(new_marks)))
            done("Added " + new_name.strip())

with tab_edit:
    if all_df.empty:
        st.info("No students yet. Add one first.")
    else:
        labels = {int(r.id): f"{r.name} ({r.branch})" for r in all_df.itertuples()}
        sid = st.selectbox("Choose a student", list(labels),
                           format_func=lambda i: labels[i], key="edit_pick")
        row = all_df[all_df["id"] == sid].iloc[0]

        with st.form("edit_form"):
            e_name = st.text_input("Name", value=row["name"], key=f"e_name_{sid}")
            e_branch = st.selectbox(
                "Branch", BRANCHES, key=f"e_branch_{sid}",
                index=BRANCHES.index(row["branch"]) if row["branch"] in BRANCHES else 0)
            e_marks = st.number_input("Marks", 0, 100, int(row["marks"]), key=f"e_marks_{sid}")
            save = st.form_submit_button("Save changes")
        if save:
            run("UPDATE students SET name=%s, branch=%s, marks=%s WHERE id=%s",
                (e_name.strip(), e_branch, int(e_marks), int(sid)))
            done("Student updated")

        st.divider()
        sure = st.checkbox("I am sure I want to delete this student", key=f"sure_{sid}")
        if st.button("Delete student", disabled=not sure):
            run("DELETE FROM students WHERE id=%s", (int(sid),))
            done("Student deleted")

What students should notice

  • load() is the only function that reads the table, and run() from db.py does all the database work. Same pattern as Part 1.
  • done() uses st.rerun() so the metrics, chart and table refresh right after a change. st.session_state keeps the success message across that rerun.
  • Each widget has a unique key. Without keys, two widgets with the same label can clash.
  • The delete button stays disabled until the checkbox is ticked. A small safety step, and easy to write.
  • Run pgAdmin next to the browser to show that every click changes real rows.

Share the app on the lab network: run streamlit run web_app.py --server.address 0.0.0.0, then other computers open http://TEACHER-IP:8501. Only do this on a trusted network, because anyone who opens the page can edit the data.

Step 6Upgrade: a second table and a JOIN

Real databases have related tables. We add a departments table and link each student to it with a foreign key (dept_id). Create setup_v2.py and run it once with python setup_v2.py:

from db import run

steps = [
    """CREATE TABLE IF NOT EXISTS departments (
           id SERIAL PRIMARY KEY,
           name VARCHAR(50) UNIQUE NOT NULL)""",
    "INSERT INTO departments (name) VALUES ('CSE'),('ECE'),('EEE'),('MECH'),('CIVIL') ON CONFLICT DO NOTHING",
    "ALTER TABLE students ADD COLUMN IF NOT EXISTS dept_id INTEGER REFERENCES departments(id)",
    "UPDATE students SET dept_id = d.id FROM departments d WHERE students.branch = d.name",
]
for sql in steps:
    run(sql)
print("Upgrade done")

Now change web_app.py in four places so the app reads departments through a JOIN:

# 1. Replace the BRANCHES line: dropdown choices now come from the database
BRANCHES = [r[0] for r in run("SELECT name FROM departments ORDER BY name", fetch=True)]

# 2. Replace the query inside load(): the JOIN returns the department name
rows = run("""SELECT s.id, s.name, d.name, s.marks
              FROM students s LEFT JOIN departments d ON d.id = s.dept_id
              WHERE s.name ILIKE %s ORDER BY s.id""", ("%" + search + "%",), fetch=True)

# 3. Replace the INSERT: it now also stores dept_id
run("INSERT INTO students (name, branch, marks, dept_id) "
    "VALUES (%s, %s, %s, (SELECT id FROM departments WHERE name = %s))",
    (new_name.strip(), new_branch, int(new_marks), new_branch))

# 4. Replace the UPDATE the same way
run("UPDATE students SET name=%s, branch=%s, marks=%s, "
    "dept_id=(SELECT id FROM departments WHERE name = %s) WHERE id=%s",
    (e_name.strip(), e_branch, int(e_marks), e_branch, int(sid)))

Then add a summary table at the end of the View tab, built with JOIN and GROUP BY:

rows = run("""SELECT d.name, COUNT(s.id), ROUND(AVG(s.marks), 1)
              FROM departments d LEFT JOIN students s ON s.dept_id = d.id
              GROUP BY d.name ORDER BY d.name""", fetch=True)
st.subheader("Department summary")
st.dataframe(pd.DataFrame(rows, columns=["Department", "Students", "Average marks"]), hide_index=True)

Discussion question: the table now stores the branch twice, as text in branch and as a number in dept_id. Why is that poor design? (Answer: redundancy can make the two disagree. In a normalized design you would drop branch. We keep it here only so the Part 2 app keeps working.)

Why LEFT JOIN and not JOIN?

A plain JOIN drops any student whose dept_id is empty. LEFT JOIN keeps every student and shows an empty department instead, so no row silently disappears from the table.

Step 7Upgrade: a login page

Only signed-in users should edit data. Passwords are never stored as plain text. We store a salted hash, a one-way scrambled value, so even a stolen table does not reveal the passwords. Create auth.py:

import hashlib, hmac, os
from db import run

def hash_password(password, salt=None):
    salt = salt or os.urandom(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 200_000)
    return salt.hex() + ":" + digest.hex()

def check_password(password, stored):
    salt_hex, digest_hex = stored.split(":")
    new = hash_password(password, bytes.fromhex(salt_hex)).split(":")[1]
    return hmac.compare_digest(new, digest_hex)

def create_user(username, password):
    run("INSERT INTO users (username, password_hash) VALUES (%s, %s) "
        "ON CONFLICT (username) DO NOTHING", (username, hash_password(password)))

def login_user(username, password):
    rows = run("SELECT password_hash FROM users WHERE username = %s", (username,), fetch=True)
    return bool(rows) and check_password(password, rows[0][0])

Create setup_users.py, run it once, then change the password lab123 to your own:

from db import run
from auth import create_user

run("""CREATE TABLE IF NOT EXISTS users (
       id SERIAL PRIMARY KEY,
       username VARCHAR(50) UNIQUE NOT NULL,
       password_hash TEXT NOT NULL)""")
create_user("admin", "lab123")
print("Admin user ready")

In web_app.py, paste this block right after st.set_page_config(...) and before st.title(...):

from auth import login_user

if not st.session_state.get("user"):
    st.title("Sign in")
    with st.form("login"):
        u = st.text_input("Username", key="login_user")
        p = st.text_input("Password", type="password", key="login_pass")
        go = st.form_submit_button("Sign in")
    if go:
        if login_user(u, p):
            st.session_state["user"] = u
            st.rerun()
        else:
            st.error("Wrong username or password.")
    st.stop()

st.sidebar.write("Signed in as " + st.session_state["user"])
if st.sidebar.button("Sign out"):
    del st.session_state["user"]
    st.rerun()
  • st.stop() ends the script early, so nothing below the login form is shown or run until the user signs in.
  • st.session_state remembers the signed-in user between reruns of the script.

This is a learning login, not production security. Streamlit forgets the session when the browser tab is refreshed, and there is no limit on wrong attempts. Real systems add HTTPS, lockouts and a proven authentication service.

Check yourself

Students answer first, then click the question to see the answer.

1. The table shows old data right after an insert. What is the most likely cause?

The display code runs before the insert code. A Streamlit script runs top to bottom, so the write must come first, or the code must call st.rerun().

2. Why do we write %s instead of putting the name into the SQL with an f-string?

An f-string lets a user type SQL into the text box (SQL injection). With %s the driver sends the value separately, so it is always treated as data.

3. What does st.session_state do?

It stores values, such as the signed-in user or a message, so they survive the script rerunning after each click.

4. Why store a password hash instead of the password?

A hash cannot be reversed. If someone copies the users table, they still do not have the passwords. The salt makes two equal passwords produce different hashes.

5. A student has no department. Which join still shows that student, JOIN or LEFT JOIN?

LEFT JOIN. It keeps every row from the left table (students) even when there is no match on the right.

6. Why do we write int(sid) before sending a value from a DataFrame to PostgreSQL?

pandas gives NumPy numbers, and the psycopg2 driver cannot convert numpy.int64. Wrapping the value in int() gives a plain Python integer.
