Chapter One Basic

Why We Convert, and What Changes

In the ER course you learned that database design happens in three stages: conceptual, then logical, then physical. Your ER/EER diagram finished the conceptual stage. It describes what exists and how things relate, but it cannot be typed into a database. A database management system such as MySQL, PostgreSQL, or Oracle understands only one kind of structure: the table (formally, the relation).

This handbook covers the second stage, the logical design: translating every shape on your diagram into tables, columns, primary keys, and foreign keys. This translation is called ER-to-relational mapping. It is largely mechanical. Once you know the rule for each shape, you can convert any diagram step by step, and two people following the rules will arrive at nearly identical schemas.

Definition

ER-to-relational mapping is the systematic process of converting a conceptual ER/EER schema into a relational schema: a set of relation (table) definitions, each with a name, a list of attributes (columns), a primary key, and any foreign keys and other integrity constraints needed to preserve the meaning of the original diagram.

What exists in ER but not in tables

The relational model is deliberately simple. Each cell of a table must hold exactly one atomic value, and tables cannot contain other tables. That simplicity is why the conversion needs rules. Several things your ER diagram expresses naturally have no direct equivalent in a table:

ER conceptWhy a table can't hold it directlyWhat we do instead
Relationship (diamond)Tables have no "lines" or "diamonds."Represent the connection with a foreign key, or with a separate table of foreign keys.
Composite attributeA cell can't contain sub-cells.Flatten it into its component columns.
Multivalued attributeA cell can't hold a list of values.Move the values into a separate table, one row per value.
Derived attributeA stored value can go out of date.Don't store it. Compute it with a query or view.
Weak entityEvery table needs a key that is unique by itself.Borrow the owner's key and combine it with the partial key.
ISA hierarchy, category, aggregationTables have no inheritance.Use one of several table layouts, linked by keys (Part IV).

A useful way to think about it: in the ER diagram, lines connect things. In the relational schema, matching values connect things. If a row in EMPLOYEE contains Dept_ID = 'D2', that value is the line to department D2. Almost every rule in this handbook applies that one idea.

A question students often ask

"Couldn't I skip the ER diagram and go straight to tables?" You can, but the diagram is where you decided things like "can an employee exist without a department?" and "can a student take the same course twice?" The mapping rules turn each of those decisions into a specific constraint: NOT NULL, UNIQUE, or a composite primary key. Without the diagram those decisions are never made explicitly, and they end up as bugs.

The integrity constraints we will use

  • Entity integrity: no primary-key column may be NULL. This is why every relation must have a real key, and why a weak entity must borrow one.
  • Referential integrity: every non-NULL foreign-key value must exist as a primary-key value in the referenced table. You cannot give a student Dept_ID = 'XYZ' if no department XYZ exists.
  • Key constraint: PK and UNIQUE column values cannot repeat. This is how we enforce the "1" in 1:1 relationships.
  • NOT NULL: this column must always have a value. This is how we enforce total participation.
  • CHECK: an arbitrary row-level condition, e.g. CHECK (Salary > 0).

Referential actions: what happens on delete?

The order to apply the rules in

The rules depend on each other. You can't add a foreign key pointing at a table whose primary key you haven't decided yet. So always apply them in this order:

  1. Strong entities (Rules 1–2): flatten composites, skip derived and multivalued attributes for now.
  2. Weak entities (Rule 5): these need their owner's PK, which now exists. If a weak entity's owner is itself weak, do the owner first.
  3. Binary 1:1 relationships (Rule 6).
  4. Binary 1:N relationships (Rule 7), including recursive 1:N (Rule 9).
  5. Binary M:N relationships (Rule 8), including recursive M:N.
  6. Multivalued attributes (Rule 3).
  7. N-ary relationships (Rule 10).
  8. Specialization / generalization (Rule 11), then categories (Rule 12).
  9. Aggregation (Rule 13): needs the inner relationship's table to already exist.
  10. Derived attributes (Rule 4): write the views last, once every base column exists.
A question students often ask

"Do I get one table per shape?" No, and this is the most important thing to understand early. Entities usually get a table. Relationships sometimes do: M:N and n-ary always do, while 1:1 and 1:N usually become just a column. Attributes usually become columns, except multivalued ones, which become tables. Chapter 20 turns this into a reliable counting procedure.

Chapter Four Basic

Rule 1: Strong Entities, Simple and Key Attributes

A strong entity has its own key attribute and doesn't depend on anything else to exist, so it maps directly to a table. Each entity instance becomes one row, and each simple attribute becomes one column.

Mapping Rule 1: Strong entity

For each strong entity set E, create a relation R with the same name. Include every simple attribute of E as a column. Choose one key attribute of E as the primary key of R. If E has other key (candidate) attributes, keep them as columns and declare them UNIQUE. Composite, multivalued, and derived attributes follow Rules 2, 3, and 4.

Choosing the primary key when there are several candidates

When an entity has more than one key, pick the PK using these criteria, in order:

  1. Never NULL, never changes. Email addresses change and phone numbers get reassigned. A roll number is assigned once and never changes.
  2. Short and simple. The PK will be copied into every table that references this one, so a 4-byte integer is better than a 100-character string.
  3. Meaningful to the business (if the other two tie). Users search by roll number, not by an internal counter.

Variation: the key attribute is itself composite

Sometimes the underlined key is a composite attribute, e.g. a CLASSROOM identified by Room = (Building, Room_No), because "Room 101" exists in every building. Flatten it (Rule 2), and the PK becomes the set of component columns:

CLASSROOM
BuildingRoom_NoCapacityHas_Projector

PK: (Building, Room_No), a composite primary key. Neither column is unique alone; the pair is.

Variation: the entity has no natural key

In a correct ER diagram every strong entity has a key (ER course, Mistake 12). If the real world genuinely offers none, for example a COMPLAINT submitted anonymously, add a surrogate key: an artificial, system-generated number such as Complaint_ID. It has no business meaning; it exists purely so every row can be identified.

CREATE TABLE COMPLAINT (
    Complaint_ID  INT  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- surrogate key
    Filed_On      DATE NOT NULL,
    Description   VARCHAR(1000) NOT NULL
);   -- MySQL: Complaint_ID INT AUTO_INCREMENT PRIMARY KEY
Most common mistake with Rule 1

Adding columns for the entity's relationships at this stage, e.g. putting Course_ID into STUDENT because "students take courses." Rule 1 uses only the entity's own attributes. Relationship columns are added later by Rules 6 to 10, and for an M:N relationship like enrolment, a column in STUDENT is actually wrong (Chapter 11).

Chapter Five Basic

Rule 2: Composite Attributes

A composite attribute is a group of sub-attributes: Name = First_Name + Last_Name. A table cell can't contain sub-cells, so the group has to be flattened.

Mapping Rule 2: Composite attribute

Do not create a column for the composite attribute itself. Create one column for each of its leaf (simple) components. If a component is itself composite, keep going down until you reach simple attributes. The composite's name survives only as a naming prefix if you want one (Addr_City).

Result: 1 table, 6 columns

STUDENT
Roll_NoFirst_NameLast_NameStreetCityPin_Code

Neither "Name" nor "Address" appears as a column. Only the leaves survive.

CREATE TABLE STUDENT (
    Roll_No     INT          PRIMARY KEY,
    First_Name  VARCHAR(50)  NOT NULL,
    Last_Name   VARCHAR(50),
    Street      VARCHAR(100),
    City        VARCHAR(50),
    Pin_Code    CHAR(6)
);

Nested composites: keep going down

If Street were itself composite (House_No, Street_Name, Area), the columns would be House_No, Street_Name, Area, City, Pin_Code. The rule is always "leaves only," however deep the tree goes.

Name collisions: prefix with the parent

If an entity has two composites with the same component names, such as Home_Address and Office_Address each with City, prefix the components: Home_City, Office_City. Two columns in one table can never share a name.

"Why not just keep one Name column? It's simpler."

You can, if the system truly never needs the parts separately. But then sorting by surname or greeting someone by first name means string-splitting every row, and "Shah, Riya" versus "Riya Shah" formats will creep in. The ER designer drew Name as composite precisely because the parts matter. Rule 2 preserves that decision. If the parts don't matter, the ER diagram should have drawn Name as a simple attribute in the first place.

Most common mistake with Rule 2

Keeping both the composite and its components: Name, First_Name, and Last_Name all as columns. Now the same fact is stored twice and the copies can disagree ("Riya Shah" in Name, "Riya Mehta" after a Last_Name update). Store the leaves only. If you want the full name, compute it: First_Name || ' ' || Last_Name (or CONCAT(...) in MySQL).

Chapter Six Basic

Rule 3: Multivalued Attributes

A multivalued attribute (double oval) can hold several values for one entity: a student with three phone numbers. This is the first rule where an attribute produces a whole new table, because a relational cell must hold exactly one value (the First Normal Form requirement).

Mapping Rule 3: Multivalued attribute

For each multivalued attribute A of entity E, create a new relation containing (1) the primary key of E, as a foreign key back to E, and (2) the attribute A (or all of A's components if A is also composite). The primary key of the new relation is E's key + A. Use ON DELETE CASCADE: phone numbers of a deleted student have no meaning.

Why the primary key is (Roll_No, Phone) and not just one of them

  • Roll_No alone repeats (101 appears twice), so it can't be the PK.
  • Phone alone might repeat too: two siblings sharing a home landline. Even if it didn't, it wouldn't express the fact that we store pairs.
  • (Roll_No, Phone) is unique: the same student listing the same number twice is exactly the duplicate we want to prevent.

Why not Phone1, Phone2, Phone3 or a comma-separated list?

Wrong: repeating columns STUDENT(Roll_No, Name, Phone1, Phone2, Phone3). Most students have NULL in Phone2 and Phone3, a fourth phone is impossible without altering the table, and "who has the number 98250 11111?" must check three columns.
Right: separate table STUDENT_PHONE(Roll_No, Phone). Unlimited phones, no NULLs, and one simple WHERE Phone = ... answers every search.
Wrong: a list in one cell Phone = '98250 11111, 99090 22222'. This violates First Normal Form. The DBMS can't validate, index, or join individual numbers, and removing one number means string surgery.
Right One value per cell, one row per value. If you ever feel the urge to put a comma inside a cell, you have found a multivalued attribute that needs its own table.

Variation: a composite multivalued attribute

Suppose each phone also records a type (Home / Work / Mobile). Phone is now multivalued and composite: {(Phone_No, Phone_Type)}. Apply Rule 3, then Rule 2 inside it: the new table gets all leaf components.

PK: (Roll_No, Phone_No). Phone_Type is not in the key: one number has one type for a given student.

As the ER course's Mistake 7 warns, once a multivalued attribute gains several details of its own, it may deserve to be modeled as a weak entity instead. The mapped tables come out almost identical, which is a nice confirmation that both views are consistent.

Most common mistake with Rule 3

Putting two different multivalued attributes into one table, e.g. STUDENT_CONTACT(Roll_No, Phone, Email) for a student with 2 phones and 3 emails. There is no natural pairing between "phone #1" and "email #2," so you either invent fake pairings or store every combination (2 × 3 = 6 rows), which multiplies redundancy. Each multivalued attribute gets its own table: STUDENT_PHONE and STUDENT_EMAIL.

Chapter Seven Basic

Rule 4: Derived Attributes

A derived attribute (dashed oval) is computed from other data: Age from Date_of_Birth, Total_Amount from line items, No_of_Employees by counting rows. Storing it creates a second copy of information that already exists, and that copy starts going stale immediately. Age changes every birthday, but a stored Age column doesn't update itself.

Mapping Rule 4: Derived attribute

Do not create a column for a derived attribute. Make sure the attribute(s) it is derived from are stored, then compute the value when needed: in a query, in a view, or, for simple same-row formulas, a generated column. Store it physically only as a deliberate, documented performance decision (see below).

When storing a derived value is acceptable

Professionals sometimes store a derived value on purpose, which is called denormalization, when computing it is very expensive and it is read far more often than its inputs change (e.g. a cached Total_Followers on a social-media profile). If you do this, you take on the job of keeping it in sync, usually with a trigger. At the logical-design stage and in exams, the expected answer is: don't store it.

Pro tip: "derived today" isn't always derived

An order's Unit_Price looks derivable from the product catalogue, but the catalogue price changes next month while the order must remember the price actually charged. That is a historical fact, not a derived attribute, and it must be stored. Before dropping a column as "derived," ask: would recomputing it tomorrow give the same answer?

Most common mistake with Rule 4

Dropping the derived attribute and forgetting its source. If the ER diagram shows a dashed Age but no Date_of_Birth, a student who follows Rule 4 blindly ends up with nothing to compute Age from. A derived attribute on the diagram is a promise that its base data exists. If the base attribute is missing, add it (and point out the gap). You'll meet exactly this situation in the Library example, Chapter 18.

Chapter Eight Intermediate

Rule 5: Weak Entities and Identifying Relationships

A weak entity can't be identified by its own attributes. "Item 1" exists in every order. It borrows identity from its owner, and it can't exist without it. The mapping has to reproduce both facts: borrowed identity (the owner's key becomes part of the PK) and existence dependency (deleting the owner deletes the weak rows).

Mapping Rule 5: Weak entity

For each weak entity W with owner E, create a relation containing all of W's simple attributes (flattened per Rule 2) plus the primary key of E as a foreign key. The primary key of the new relation is E's key + W's partial key. Declare the FK ON DELETE CASCADE. The identifying relationship (double diamond) produces no table of its own. The FK is that relationship, and any attributes on the identifying relationship go into W's table.

Pro tip: surrogate keys on weak entities

Many real systems give weak-entity tables an auto-generated Order_Item_ID as PK for convenience (shorter FKs pointing at them, friendlier ORMs). That is fine in practice, provided you still declare UNIQUE (Order_No, Item_No). Without it, nothing stops two "item 1" rows in the same order, and you've silently lost the partial-key constraint. In exams, give the textbook answer: composite PK (owner key + partial key).

Most common mistakes with Rule 5
  • Using the partial key alone as the PK. PRIMARY KEY (Item_No) fails the moment a second order also has an item 1.
  • Creating a separate table for the identifying relationship (CONTAINS(Order_No, Item_No)). It is pure duplication, because ORDER_ITEM already holds both columns.
  • Forgetting ON DELETE CASCADE, so deleting an order is either blocked or leaves orphan items, which breaks existence dependency.
  • Declaring a two-level composite FK as two single-column FKs, e.g. Building_ID → BUILDING and Floor_No → ??? (see Mistake 18).

Rule 6: Binary One-to-One (1:1)

Every binary relationship rule answers one question: where does the foreign key go? For 1:1 there are three legitimate answers. Participation decides which one is best.

Mapping Rule 6: Binary 1:1 relationship between S and T
  1. Foreign-key approach (default). Pick one side, say S, and add T's primary key to S as a foreign key, declared UNIQUE. Put the relationship's attributes in S too. Choose S to be the entity with total participation, so the FK is never NULL.
  2. Merged-relation approach. If both sides have total participation, the two entities always come in pairs, so you may merge them into a single table.
  3. Cross-reference approach. If both sides are partial and few instances participate, create a separate table holding both keys, each declared UNIQUE.

Most common mistakes with Rule 6
  • Forgetting UNIQUE on the FK, which turns the 1:1 into 1:N (Mistake 10).
  • Putting FKs in both tables (Mgr_ID in DEPARTMENT and Managed_Dept in EMPLOYEE). This stores the same fact twice, the two copies can contradict each other, and you can no longer insert either row first.

Rule 7: Binary One-to-Many (1:N)

1:N is the most common relationship in real schemas, and its rule is one short sentence: the foreign key goes on the "many" side. The reason is a cell-counting argument. Each employee belongs to one department, so one cell per employee row is enough. Each department has many employees, which would need a list in one cell, and lists aren't allowed.

Mapping Rule 7: Binary 1:N relationship

Let S be the entity on the N side and T the entity on the 1 side. Add T's primary key to S's table as a foreign key. Add the relationship's attributes to S's table as well. If S participates totally, declare the FK NOT NULL. No new table is created.

Why the relationship attribute goes on the N side

"Since" describes one (department, employee) pairing. Each employee is in exactly one such pairing, so an employee row has room for exactly one "Since" value. A department row would need one "Since" per employee, which is a list again. Relationship attributes always travel with the foreign key.

The wrong way, shown with data

Wrong: FK on the "1" side DEPARTMENT(Dept_ID, Dept_Name, Emp_ID) would need a row (D1, 'Sales', E01) and (D1, 'Sales', E02). Dept_ID is no longer unique and Dept_Name is duplicated, or you end up with a list of employee IDs in one cell.
Right: FK on the "N" side EMPLOYEE(..., Dept_ID). Each employee row stores one department. The department is stored once. Nothing repeats except the FK value, and that repetition is the relationship.

Variation: optional 1:N with very sparse participation

If the N side participates partially, the FK is nullable (ON DELETE SET NULL is often natural). If only a tiny fraction participates, e.g. 3 out of 10,000 books are "on reserve for" a course, the FK column would be 99.97% NULL. Some designers then use a separate relationship table RESERVE(ISBN, Course_ID) with PK = ISBN (the N side's key, which keeps it 1:N). Both designs are correct. The FK approach is the default and the exam answer.

The 10-second test for 1:N

Say the sentence "one ___ has many ___." The entity after "many" gets the foreign key. "One department has many employees" → FK in EMPLOYEE. "One customer places many orders" → FK in ORDERS. "One librarian manages many books" → FK in BOOK.

Rule 8: Binary Many-to-Many (M:N)

In an M:N relationship neither side can hold the FK. A student takes many courses, so a single Course_ID cell in STUDENT isn't enough, and a course has many students, so a Roll_No cell in COURSE isn't enough either. The relationship needs a table of its own. It is often called a junction, bridge, link, or associative table.

Mapping Rule 8: Binary M:N relationship

Create a new relation R for the relationship. Include the primary keys of both participating entities as foreign keys, plus all of the relationship's attributes. The primary key of R is the combination of the two foreign keys. Use ON DELETE CASCADE on both FKs in most cases: an enrolment record is meaningless once the student or the course is gone.

What plain constraints cannot enforce

Some participation constraints are on the side that does not hold the foreign key:

  • Total participation on the "1" side of 1:N. "Every department must have at least one employee." The FK lives in EMPLOYEE, and nothing in the DEPARTMENT row can force some employee row to reference it.
  • Total participation in an M:N. "Every course must have at least one student enrolled." The link rows live in ENROLLS, and COURSE can't require them.
  • Specific maximums such as "a student takes at most 6 courses," i.e. (0,6) instead of (0,N).

These require triggers, assertions (in the SQL standard but rarely implemented), or checks in application code. In an exam, write the schema and add a note such as "Total participation of DEPARTMENT in employs cannot be enforced by FK constraints; requires a trigger/assertion." That note often earns the last mark.

-- Standard SQL assertion (conceptual; most DBMSs don't support CREATE ASSERTION)
CREATE ASSERTION every_dept_has_staff CHECK (
    NOT EXISTS (SELECT * FROM DEPARTMENT D
                WHERE NOT EXISTS (SELECT * FROM EMPLOYEE E WHERE E.Dept_ID = D.Dept_ID))
);
Pro tip: the chicken-and-egg insert

If DEPARTMENT.Mgr_ID is NOT NULL (Rule 6, every department has a manager) and EMPLOYEE.Dept_ID is NOT NULL (every employee works somewhere), you can't insert the first row of either table: each needs the other to exist first. Solutions: (1) make one of the two FKs nullable and fill it in with an UPDATE; (2) create the tables without that FK and add it later with ALTER TABLE ... ADD FOREIGN KEY; or (3) in PostgreSQL/Oracle, declare it DEFERRABLE INITIALLY DEFERRED so it is checked only at COMMIT.

Most common mistake here

Putting NOT NULL on the wrong side. The double line into EMPLOYEE means EMPLOYEE must participate, so the FK column in EMPLOYEE is NOT NULL. Students often read the double line as belonging to the table at the other end. Rule of thumb: the double line touches the entity whose FK becomes NOT NULL (when that entity holds the FK).

Rule 9: Unary (Recursive) Relationships

In a recursive relationship an entity relates to other instances of itself: an employee supervises employees, a course is a prerequisite of courses, a person is married to a person. The mapping rules are exactly Rules 6, 7, and 8. The only twist is that both ends point at the same table, so each end needs a distinct role name.

Mapping Rule 9: Recursive relationship on entity E
  • 1:N: add a second column to E, named after the "1"-side role (e.g. Supervisor_ID), as an FK referencing E's own PK. It is usually nullable, since someone is at the top.
  • 1:1: same as 1:N, plus UNIQUE on the FK.
  • M:N: a new table with two FKs to E, each given a role name (e.g. Course_ID, Prereq_ID). PK = both.

  • Reusing the PK name for the FK, i.e. two columns called Emp_ID. That is impossible in one table, and in the M:N case it makes the table unreadable. Always name FKs after their role: Supervisor_ID, Prereq_ID, Spouse_ID, Referred_By.
  • Creating a separate SUPERVISOR table copying employee data. A supervisor is an employee, and the recursive FK already says so.
  • Making the recursive FK NOT NULL in a hierarchy: then someone must be at the top with no supervisor, but the column won't allow it.

Rule 10: Ternary and N-ary Relationships

A ternary relationship records a single fact about three entities at once: "supplier S supplies part P for project J." There is no single "N side" to hold an FK, so, like M:N, it always gets a table of its own.

Mapping Rule 10: n-ary relationship (degree ≥ 3)

Rule 11: Specialization and Generalization

Tables have no inheritance, so an ISA hierarchy has no single correct mapping. There are four standard options, and the right one depends on the two constraints you marked on the diagram (disjoint/overlapping and total/partial) plus a few practical factors. Specialization and generalization map identically, because the finished diagrams are identical (ER course, Chapter 8).

Mapping Rule 11: Specialization with superclass C and subclasses S1…Sm (choose one)
  • Option A: superclass table + one table per subclass. C gets its own table with its attributes. Each Si gets a table with C's key (as both PK and FK to C) plus Si's own attributes. Works for every constraint combination.
  • Option B: subclass tables only. No table for C. Each Si's table holds C's key, all of C's attributes, and Si's own. Only valid when the specialization is total, and best when it is disjoint.
  • Option C: one table with a single type attribute. One table holding C's attributes, every subclass's attributes, and a discriminator column (e.g. Staff_Type). Only for disjoint specializations.
  • Option D: one table with a Boolean flag per subclass. Like C, but with one yes/no column per subclass (Is_Doctor, Is_Nurse). Designed for overlapping specializations (also works for disjoint).

Multi-level hierarchies and shared subclasses

Apply the rule level by level, top-down. With Option A, the root's key propagates all the way down: if ENGINEER specializes further into SOFTWARE_ENGINEER, then SOFTWARE_ENGINEER(Emp_ID, Language) with Emp_ID → ENGINEER(Emp_ID). A shared subclass (multiple inheritance, e.g. TEACHING_ASSISTANT is both a STUDENT and an EMPLOYEE under a common PERSON root) gets one table whose key is the common root key, with an FK to each parent table.

Most common mistakes with Rule 11
  • Giving subclass tables their own new IDs (DOCTOR(Doctor_ID, Staff_ID, ...)). A doctor is a staff member, so it should be identified by the same key (Mistake 16).
  • Picking an option the constraints forbid: B for a partial hierarchy, or C for an overlapping one (Mistake 15).
  • Copying superclass attributes into subclass tables under Option A (Name in both STAFF and DOCTOR). This mixes A and B and duplicates data.

Rule 12: Categories (Union Types)

A category such as OWNER ⊆ PERSON ∪ BANK ∪ COMPANY has a special mapping problem. Its members come from superclasses with different keys (Aadhar_No, Branch_Code, Registration_No). There is no single existing column that could identify "an owner," so the FK in VEHICLE has nothing uniform to point at. The solution is to invent one.

Mapping Rule 12: Category with superclasses of different keys

Create a relation for the category with a new surrogate key (e.g. Owner_ID), plus the category's own attributes and usually a type discriminator. Add the surrogate key as a foreign key to each superclass's table, declared UNIQUE and nullable (superclass rows that aren't owners leave it NULL). Relationships of the category (e.g. owns) reference the surrogate key. Special case: if all superclasses share the same key, no surrogate is needed; use that key directly.

The tempting wrong answers

Wrong: a "polymorphic" reference VEHICLE(Vehicle_Reg_No, Owner_Key, Owner_Type), where Owner_Key holds an Aadhar number or a branch code or a registration number depending on the type. Right: surrogate key Every reference goes to one table (OWNER) through one real, enforced FK. Each superclass links to OWNER through its own enforced FK.

When is no surrogate needed?

If the superclasses share a key, e.g. a category REGISTERED_VEHICLE ⊆ CAR ∪ TRUCK where both are identified by the same Vehicle_ID series, just use Vehicle_ID as the category's key. The surrogate exists only to unify different keys.

Rule 13: Aggregation

Aggregation lets a relationship (MANAGER monitors …) attach to another relationship (EMPLOYEE works_on PROJECT) treated as a single unit. In tables, the inner relationship is just another table with a primary key, so the outer relationship can reference it like any entity.

Mapping Rule 13: Aggregation
  1. Map everything inside the dashed box normally (entities by Rule 1, the inner relationship by Rules 6–8).
  2. Treat the inner relationship's table as an entity whose key is that table's primary key.
  3. Map the outer relationship by the usual rule for its cardinality. Wherever an FK "to the aggregate" is needed, it is a composite FK referencing the inner relationship's table, not separate FKs to the inner entities.

  • BOOK: Genre is multivalued, so it is skipped for now.

None. Move on, but say so in an exam answer: it shows the examiner that you checked.

"One librarian manages many books," so the FK goes into BOOK. BOOK participates totally (double line), so the FK is NOT NULL. We name it by its role, Librarian_ID. It references LIBRARIAN(Employee_ID): names may differ, but types must match.

MEMBER_PHONE(Member_ID, Phone) and BOOK_GENRE(ISBN, Genre), in two separate tables (never one combined table).

Verify: can the schema answer the requirement's questions?

A schema is only correct if it can answer what the requirements ask. Two quick tests:

-- "Which books does member 7 currently have, and when are they due?"
SELECT B.Title, BR.Borrow_Date
FROM BORROWS BR JOIN BOOK B ON B.ISBN = BR.ISBN
WHERE BR.Member_ID = 7 AND BR.Return_Date IS NULL;

-- "Which librarian is responsible for each Fantasy book?"
SELECT B.Title, L.Name
FROM BOOK B
JOIN BOOK_GENRE G ON G.ISBN = B.ISBN
JOIN LIBRARIAN  L ON L.Employee_ID = B.Librarian_ID
WHERE G.Genre = 'Fantasy';
Pro reflection: mapping exposes modeling gaps

Mapping is a great second review of the ER diagram. Here it revealed two things: (1) Age had no base attribute, and (2) BOOK is keyed by ISBN, which identifies a title, not a physical copy. A library with three copies of the same ISBN can't record which copy Riya has. The right fix is upstream, in the ER diagram: add a weak entity BOOK_COPY (partial key Copy_No) owned by BOOK, and make borrows relate MEMBER to BOOK_COPY. When mapping feels awkward, suspect the diagram first.

Chapter Twenty-One All levels

Mistakes to Avoid When Mapping

These are the errors that show up again and again in assignments and exams, roughly in order of how often they appear. Each one breaks a specific guarantee that the ER diagram made, which is a good way to remember why it's wrong.

Creating one table for every shape on the diagram

Diamonds don't automatically become tables. A separate table for every 1:N relationship, or for the identifying relationship of a weak entity, adds joins and duplicate data without adding information.

Over-tabledEMPLOYEE, DEPARTMENT, and WORKS_IN(Emp_ID, Dept_ID) for a 1:N relationship.
CorrectEMPLOYEE(…, Dept_ID) and DEPARTMENT. The FK is the relationship.

Putting the 1:N foreign key on the "1" side

The "1" side would need a list of IDs per row. Use the sentence test: "one department has many employees." The word after "many" names the table that gets the FK.

WrongDEPARTMENT(Dept_ID, Dept_Name, Emp_ID): either the department repeats per employee, or Emp_ID holds a list.
RightEMPLOYEE(Emp_ID, Name, Dept_ID).

Mapping an M:N relationship with a foreign-key column

A single FK cell can hold one value, but M:N needs many on both sides. Students end up duplicating whole entity rows per partner.

WrongSTUDENT(Roll_No, Name, Course_ID): to take 5 courses, Riya needs 5 rows, so Roll_No can't be the PK and her Name is stored 5 times.
RightENROLLS(Roll_No, Course_ID, Grade) with PK (Roll_No, Course_ID).

Putting relationship attributes in the wrong table

A relationship attribute describes a pairing, so it must live wherever one row represents one pairing.

WrongGrade in STUDENT (which course's grade?) or in COURSE (whose grade?).
RightM:N: in the link table. 1:N: in the N-side table next to the FK. 1:1: next to the FK.

Keeping a composite attribute as one column, or keeping it and its parts

A single Address string can't be filtered by city. Storing Name alongside First_Name/Last_Name duplicates data that can drift apart.

WrongSTUDENT(Roll_No, Name, First_Name, Last_Name)
RightSTUDENT(Roll_No, First_Name, Last_Name). Leaves only.

Storing a multivalued attribute as repeating columns or a list

Phone1, Phone2, Phone3 sets an arbitrary limit and fills rows with NULLs. '98250..., 99090...' in one cell breaks First Normal Form and makes searching and validation impossible.

WrongMEMBER(Member_ID, Phone1, Phone2)
RightMEMBER_PHONE(Member_ID, Phone), PK both.

Combining two multivalued attributes into one table

Phones and emails have no natural pairing. One table for both forces fake pairings or a cross product (2 phones × 3 emails = 6 rows of junk).

WrongCONTACT(Roll_No, Phone, Email)
RightSTUDENT_PHONE(Roll_No, Phone) and STUDENT_EMAIL(Roll_No, Email).

Storing derived attributes, or dropping their source

A stored Age is wrong the day after someone's birthday. Conversely, dropping Age is only safe if Date_of_Birth is stored.

WrongLIBRARIAN(Employee_ID, Name, Age)
RightLIBRARIAN(Employee_ID, Name, Date_of_Birth) + a view computing Age.

Using the partial key alone as a weak entity's primary key

A partial key is unique only within one owner, which is the whole point of a weak entity.

WrongORDER_ITEM with PRIMARY KEY (Item_No): the second order's "item 1" is rejected.
RightPRIMARY KEY (Order_No, Item_No), Order_No FK with ON DELETE CASCADE.

Forgetting UNIQUE on a 1:1 foreign key

An FK without UNIQUE allows the same value in many rows, so the "1:1" is silently a 1:N.

WrongMgr_ID CHAR(3) REFERENCES EMPLOYEE: E07 can manage D1 and D2.
RightMgr_ID CHAR(3) NOT NULL UNIQUE REFERENCES EMPLOYEE.

Ignoring participation: missing NOT NULL, or NOT NULL on the wrong side

A double line into EMPLOYEE means every employee must have a department, so the FK in EMPLOYEE is NOT NULL. Leaving it nullable loses the rule. Making a partial FK NOT NULL rejects valid data (the CEO with no supervisor).

Using just the two FKs as the key when the same pair can repeat

(Member_ID, ISBN) as the PK of BORROWS means no member can ever borrow the same book twice. Ask "can this pair happen again?" If yes, add the distinguishing attribute (a date or semester) to the key.

WrongPRIMARY KEY (Member_ID, ISBN)
RightPRIMARY KEY (Member_ID, ISBN, Borrow_Date)

Splitting a ternary relationship into three binary tables

Chapter 14 proved it with data: joining the three pairwise tables back together produces spurious tuples, facts that never happened. A genuine ternary gets one table with all three FKs.

Recursive relationships without role names

Two columns can't both be called Emp_ID. Even when they're in different tables, PREREQUISITE(Course_ID, Course_ID2) doesn't say which course requires which.

UnclearPREREQUISITE(Course_ID1, Course_ID2)
ClearPREREQUISITE(Course_ID, Prereq_ID): "Course_ID requires Prereq_ID."

Choosing a specialization option the constraints don't allow

Option B (subclass tables only) for a partial hierarchy loses every entity that belongs to no subclass. Option C (single type column) for an overlapping hierarchy can't represent an entity in two subclasses. Check the decision table in Chapter 15 before choosing.

Giving subclass tables their own new identifiers

A doctor is a staff member, with the same identity. A fresh Doctor_ID creates two IDs for one person, and a mapping between them that can break.

WrongDOCTOR(Doctor_ID, Staff_ID, Specialization)
RightDOCTOR(Staff_ID, Specialization), Staff_ID both PK and FK.

Mapping a category with a "polymorphic" reference

An Owner_Key column that sometimes holds an Aadhar number and sometimes a branch code can't be declared as an FK, so the DBMS can't enforce that the owner exists. Use the surrogate-key pattern (Rule 12).

Declaring a composite foreign key as separate single-column foreign keys

A composite FK must reference the composite PK as a unit. Two separate FKs check each column independently, so combinations that don't exist slip through.

Wrong 
FOREIGN KEY (Emp_ID)  REFERENCES EMPLOYEE,
FOREIGN KEY (Proj_ID) REFERENCES PROJECT
-- in MONITORS: accepts (E02, P2) even if
-- E02 never worked on P2
Right 
FOREIGN KEY (Emp_ID, Proj_ID)
    REFERENCES WORKS_ON(Emp_ID, Proj_ID)

Aggregation mapped to the entities instead of the relationship

This is a special case of the previous mistake. In aggregation, the outer relationship attaches to the inner relationship, so its FK must reference the inner relationship's table (Chapter 17), not EMPLOYEE and PROJECT separately.

Using SQL reserved words as table or column names

ORDER, USER, GROUP, TABLE, SELECT, DATE, KEY and similar words are reserved. CREATE TABLE ORDER (...) fails with a confusing syntax error. Rename (ORDERS, APP_USER, STUDENT_GROUP, Order_Date) rather than relying on quoting.

FK data type doesn't match the referenced PK

If DEPARTMENT.Dept_ID is CHAR(3), then EMPLOYEE.Dept_ID must be CHAR(3) too, not INT or VARCHAR(10). Many DBMSs refuse the FK outright. Others accept it and then compare values slowly or wrongly.

Referencing the superclass when only a subclass is allowed

If only doctors treat patients, PATIENT.Doctor_ID must reference DOCTOR(Staff_ID). Referencing STAFF(Staff_ID) lets a nurse's ID be recorded as the treating doctor. Always point an FK at the most specific table the ER line touches.

Chapter Twenty-Two Pro

Pro Tips and a Final Verification Checklist

1. Inventory first, map second

Before writing a single table, list every component on the diagram (as in Chapters 18 and 19) and tick each one off as you map it. Most lost marks come from simply forgetting a multivalued attribute or a relationship, not from misunderstanding a rule.

2. Adopt a naming convention and never break it

  • Tables: the entity name in UPPER_SNAKE_CASE (ORDER_ITEM). Link tables are named after the relationship verb (ENROLLS, WORKS_ON) or both entities (STUDENT_COURSE). Pick one style.
  • Multivalued tables: OWNER_ATTRIBUTE (STUDENT_PHONE, BOOK_GENRE).
  • FK columns: the same name as the referenced PK (Dept_ID) unless a role is involved (Supervisor_ID, Librarian_ID, Prereq_ID).
  • Avoid reserved words (Mistake 20).

3. Natural or surrogate keys?

Natural key (Roll_No, ISBN, Aadhar_No)Surrogate key (auto-generated ID)
MeaningMeaningful to usersNo business meaning
StabilityCan change (emails, phone numbers)Never changes
Size in FKsCan be long (ISBN is 13 characters)Usually a 4 or 8 byte integer
Required when…—No natural key exists; categories (Rule 12)
The catch—You must still add UNIQUE on the natural key, or duplicates sneak in

For exams: use the key from the ER diagram. In practice: surrogate keys are common, but never at the cost of dropping the natural uniqueness constraint.

4. Choose ON DELETE deliberately

FK comes from…Usually
Weak entity → ownerCASCADE (existence dependency)
Multivalued-attribute table → ownerCASCADE
M:N / n-ary link table → participantsCASCADE (or RESTRICT if the history must be kept)
Subclass → superclass (Option A)CASCADE
1:N FK, total participationRESTRICT
1:N FK, partial participationSET NULL

5. Create in dependency order, drop in reverse

A table can only reference tables that already exist. Create "parents" first (entities with no FKs), then children, then link tables. Drop in the opposite order. For circular references (Chapter 12's chicken-and-egg), create both tables first and add one FK afterwards with ALTER TABLE.

6. Index your foreign keys

Every join and every ON DELETE check searches the FK column. MySQL (InnoDB) indexes FKs automatically; PostgreSQL does not. At the physical-design stage, add CREATE INDEX ... ON EMPLOYEE(Dept_ID) for FKs you query.

7. Test the schema with rows and questions

Insert three or four realistic rows per table, including edge cases (a member with no phone, a book borrowed twice, an employee with no supervisor). Then write the queries the requirements imply. If a query is impossible or needs string-splitting, the mapping, or the ER diagram, has a gap.

8. Relate it to normalization

A correct mapping of a good ER diagram usually produces tables already in Third Normal Form. If you later find a normalization problem (e.g. a column that depends on only part of a composite key), it almost always points to a modeling error upstream, such as an attribute attached to the wrong entity or relationship. Fix the diagram, then re-map.

9. Write down what SQL can't enforce

Total participation on the "1" side, total/disjoint specialization under Option A, and specific maximum cardinalities all need triggers or application code. List them under your schema. This shows the reader (and the examiner) that nothing from the diagram was lost.

The final verification checklist

  • Every strong entity has a table with a primary key.
  • Every composite attribute has been flattened to its leaves, and its parent name is gone.
  • Every multivalued attribute has its own table with PK (owner key, value).
  • No derived attribute is stored, and every derived attribute's base is stored.
  • Every weak entity's PK = owner's PK + partial key, with an FK that uses ON DELETE CASCADE.
  • No table exists for any identifying relationship.
  • Every 1:N FK is on the N side, with its relationship attributes beside it.
  • Every 1:1 FK is UNIQUE, placed on the total side where possible.
  • Every M:N and n-ary relationship has its own table, and its key allows every legitimate repeat and nothing more.
  • Every total participation that sits on the FK side is NOT NULL.
  • Every recursive FK has a role name.
  • Every ISA hierarchy uses an option its constraints permit, with the choice justified.
  • Every category uses a surrogate key (or a shared key), and there are no polymorphic references.
  • Every aggregation FK references the inner relationship's table as a composite FK.
  • Every FK's data type matches its referenced PK exactly, and no name is a reserved word.
  • Constraints that SQL can't enforce are listed in a note.
