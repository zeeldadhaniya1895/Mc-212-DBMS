Chapter One

Why We Draw ER Diagrams At All

Before you learn a single symbol, it is worth understanding the problem an ER diagram is trying to solve — because every rule in this course exists to serve that purpose, and once the purpose is clear, the rules stop feeling arbitrary.

Imagine you have been asked to build the database for a university. You could, in theory, sit down and start writing CREATE TABLE statements immediately. Some students do exactly this — and it almost always produces a database with duplicated data, missing relationships, and awkward redesigns three weeks later. The reason is simple: tables are an implementation detail. Before you decide how to store something, you first need to decide, in plain language, what exists in your system and how those things relate to each other. That decision is made once, carefully, on paper — and that is exactly what an ER diagram is for.

Database design is traditionally taught in three stages:

  1. Conceptual design — What real-world things and relationships exist? This is where the ER/EER diagram lives.
  2. Logical design — How do we translate that into tables, with primary keys and foreign keys, following normalization rules?
  3. Physical design — How is it actually stored: indexes, data types, partitioning, and so on?
Definition

An Entity-Relationship (ER) Diagram is a conceptual-level diagram that models the data requirements of a system using three ingredients: entities (things), attributes (facts about those things), and relationships (associations between things) — deliberately without reference to how any of it will eventually be stored.

This separation directly explains the very first mistake we will discuss in Chapter 13: students who already know a bit about databases often can't resist drawing primary keys and foreign keys onto their ER diagram. But foreign keys are a logical-design concept — they don't exist yet at the conceptual stage.

This course uses Chen's notation throughout — the original notation proposed by Peter Chen in 1976, and still the most widely taught version because each concept gets its own distinct, unambiguous shape: rectangle for entity, oval for attribute, diamond for relationship.

Chapter Two

Entities: The Nouns of Your System

Start by reading through your requirements and circling every noun that represents a "thing" you need to store facts about. A useful test: if you can imagine a form or a spreadsheet row dedicated just to this thing, it is probably an entity.

Definition

An entity is a distinguishable real-world object or concept about which data is stored. An entity set (or entity type) is the collection of all entities of the same kind — for example, all students. A single occurrence, like "the student Riya Shah," is called an entity instance.

In Chen's notation, an entity is drawn as a plain rectangle with its name written inside.

A question students often ask

"How do I know if something should be an entity, or just an attribute of another entity?" Ask whether the "thing" in question (a) has attributes of its own that you care about, or (b) could ever need to relate to more than one instance of something else. If a department only ever needs a name, it can stay as an attribute of EMPLOYEE. The moment you also need a department's location, its budget, and the fact that multiple employees belong to the same department, it deserves to be a full entity, DEPARTMENT. We revisit this exact test in Mistake 2, with a worked comparison.

Chapter Three

Attributes: Describing an Entity, Precisely

Once you have your entities, the next question is: what do you need to know about each one? Every fact you attach to an entity is an attribute, drawn as an oval connected by a line to its entity.

Simple (atomic) attributes

A simple attribute cannot be meaningfully broken down further. Age, Gender, and Salary are typical examples, drawn as a single plain oval.

Composite attributes

A composite attribute is made up of smaller sub-parts that are each independently meaningful — Name as First_Name plus Last_Name. It is drawn as an oval with smaller ovals branching off it.

Key attributes

A key attribute uniquely identifies every instance of the entity. Drawn like a simple oval, but with the name underlined. Every strong entity must have at least one.

Multivalued attributes

A multivalued attribute can hold more than one value for a single entity instance — a student's multiple phone numbers. Drawn as a double oval.

Derived attributes

A derived attribute is computed from other attributes rather than stored directly — Age derived from Date_of_Birth. Drawn as a dashed oval.

Partial keys (for weak entities)

Covered fully in Chapter 6: a partial key distinguishes entities only within their owner's group. Drawn as an oval with a dashed underline.

Chapter Four

Relationships: Binary and Ternary

A relationship expresses a meaningful association between entities. It is drawn as a diamond, connected by lines to every entity that participates, and labeled with a verb phrase.

enrolls in
Relationship
A diamond connecting two or more entities.

Relationships can have their own attributes

A fact can belong to neither entity individually, but to the specific pairing. Grade in "a student enrolls in a course" belongs to the specific (student, course) combination, so it attaches to the diamond itself.

Degree of a relationship

  • Unary (recursive) — an entity relates to another instance of itself, e.g. EMPLOYEE supervises EMPLOYEE.
  • Binary — between two different entities. The overwhelming majority of relationships.
  • Ternary — among three entities simultaneously, in a way that cannot be broken apart without losing meaning.

A properly drawn ternary relationship

Example: a SUPPLIER supplies a PART for a specific PROJECT. This is one indivisible three-way fact — it tells you which supplier supplies which part for which project, information that would be lost if you only had three separate binary relationships. All three entities connect to a single diamond.

A common point of confusion

A ternary relationship is not the same as three binary relationships. Three separate pairs (Supplier–Part, Part–Project, Supplier–Project) cannot express which supplier supplies which part for which specific project — that combined fact only exists at the level of all three together. If your three entities don't genuinely need to be tied together simultaneously, prefer two binary relationships instead (Mistake 6, Chapter 13).

Some textbooks write cardinality and participation together as (min, max) next to each entity: max is 1 or N as before, and min is 0 (optional) or 1 (mandatory).   • Total participation (a double line): every instance must appear in this relationship.

How to decide total vs. partial

Ask, for each entity separately: "Can this thing exist without ever taking part in this relationship?" If no — draw total participation (double line). If yes — draw partial participation (single line).

Chapter Six

Weak Entities and Identifying Relationships

A weak entity is one whose instances cannot be told apart using its own attributes alone — it borrows its identity from an owner entity that it is existence-dependent on.

Definition

A weak entity has existence dependency on its owner: if the owner instance is deleted, the weak entity instance no longer makes sense. Example: an ORDER_ITEM only exists in the context of a specific ORDER — "item number 1" is meaningless without knowing which order it belongs to.

A complete weak-entity representation always has three parts together:

  1. The weak entity drawn as a double-lined rectangle.
  2. A partial key (dashed underline).
  3. An identifying relationship, drawn as a double-lined diamond, to its owner.

The weak entity's true, system-wide identity is the combination of the owner's key and its own partial key — (Order_No = 105, Item_No = 1) uniquely identifies one order item across the entire system, even though Item_No = 1 repeats across many different orders.

Chapter Seven

Worked Example: A Library Management System

The requirement, in plain English

"The library keeps track of its books and its members. Members can borrow books, and we need to record when a book was borrowed and when it is due back. Each book is looked after by one librarian, and every book must have a librarian responsible for it."

Step 1 — Identify entities

MEMBER, BOOK, LIBRARIAN.

Step 2 — Identify attributes

  • MEMBER: Member_ID (key), Name (composite), Phone (multivalued), Join_Date.
  • BOOK: ISBN (key), Title, Genre (multivalued), Publish_Year.
  • LIBRARIAN: Employee_ID (key), Name, Age (derived).

Step 3 — Identify relationships

MEMBER–borrows–BOOK (M:N, carries Borrow_Date and Return_Date). LIBRARIAN–managed by–BOOK (1:N).

Step 4 — Decide participation

A member may not have borrowed anything yet (partial). Every book must have a responsible librarian (total, on the BOOK side of "managed by").

The finished diagram

Confirm you can point to an example of every concept from Chapters 2–6 in Figure 7.1: a simple attribute, a composite attribute, a multivalued attribute, a key attribute, a relationship carrying its own attributes, M:N cardinality, 1:N cardinality, and a total-participation double line.

Chapter Eight

Enhanced ER: Specialization and Generalization

Real systems very often contain hierarchies: an EMPLOYEE might specifically be an ENGINEER or a MANAGER. Each more specific type shares everything the general type has, plus a few extra attributes of its own — the "is-a" relationship, familiar from inheritance in object-oriented programming.

Specialization: top-down

Definition

Specialization defines more specific sub-entities from a single higher-level (super) entity. A top-down way of thinking: start with the general concept and split it.

Generalization: bottom-up

Definition

Generalization is the reverse process: start with entities that already share common attributes and combine them into a new higher-level super entity.

Example: STUDENT and TEACHER both have Name, Address, Phone → generalize into a common PERSON super-entity, keeping Fee under STUDENT and Salary under TEACHER.

So... is generalization just specialization drawn backwards?

Visually, yes — the finished diagram uses the same triangle notation either way. The distinction is about your design process, not the final picture.

Inheritance

  • Attribute inheritance — every sub-entity automatically has all the super-entity's attributes, plus its own.
  • Relationship inheritance — if EMPLOYEE participates in some other relationship, ENGINEER and MANAGER can too, because they are employees.

Chapter Nine

Constraints: Disjoint, Overlapping, Total, Partial

Every "isa" hierarchy needs two independent yes/no decisions written explicitly on the diagram.

Question A — Can an entity belong to more than one subclass at once?

  • Disjoint (marked d): No — the subclasses' member sets never intersect. An employee is either an Engineer or a Manager, never both.
  • Overlapping (marked o): Yes — the subclasses' member sets can intersect. A person could be both a STUDENT and a TEACHER at once.

Because the "d"/"o" decision is really a question about whether the two subclasses' membership sets can overlap, it helps to see it as a Venn diagram — the same picture you'd draw for a set-intersection problem in mathematics:

Question B — Must every super-entity instance belong to some subclass?

  • Total specialization (double line): Yes — every super-entity instance must fall into at least one subclass.
  • Partial specialization (single line): No — some super-entity instances might belong to none of the defined subclasses.
CombinationMeaningExample
Disjoint + TotalEvery instance belongs to exactly one subclass, no exceptions.Every EMPLOYEE is either an ENGINEER or a MANAGER, never both.
Disjoint + PartialAt most one subclass; some instances belong to none.Some employees are ENGINEER or MANAGER; interns fit neither.

Chapter Ten

Aggregation

What if a relationship needs to connect to another relationship, rather than to an entity? A diamond cannot directly attach to another diamond. Aggregation is the EER device built to solve exactly this.

Definition

Aggregation treats an entire existing relationship — together with the entities it connects — as if it were a single abstract entity, so a new relationship can be drawn to that combined unit.

Example: EMPLOYEE works_on PROJECT already exists. Now a MANAGER needs to monitor that specific assignment — a fact about the pairing, not about either entity alone. We draw a dashed boundary around the whole EMPLOYEE–works_on–PROJECT group and connect "monitors" to that boundary.

How do I know when I need aggregation instead of another relationship?

Ask whether the new fact genuinely depends on the pairing, not on either entity alone. If MANAGER simply needed to monitor employees in general, you'd draw a normal binary relationship — no aggregation needed.

Chapter Eleven

Union Types (Category): A Subclass of Several Distinct Superclasses

Specialization and generalization both assume every subclass shares one single superclass. But sometimes a subclass's members are drawn from the union of several genuinely different superclasses that don't otherwise have anything in common. This needs a fourth EER construct: the category (also called a union type).

Definition

A category represents a subclass that is a subset of the union of two or more distinct superclasses, each of which may have its own separate key and its own unrelated attributes. This is different from specialization, where all subclasses come from one common superclass. It is drawn as a circle containing a U, with lines from each superclass converging into it, and a single line down to the category entity.

Classic example: a vehicle needs to record its OWNER. An owner might be a PERSON, a BANK (if the vehicle is financed), or a COMPANY (if it's a company car). These three superclasses have almost nothing in common — a person's attributes (Age, Aadhar_No) look nothing like a bank's (Branch_Code) or a company's (Registration_No). It would make no sense to force them all into one shared "specialization" superclass just so OWNER could specialize from it. Instead, OWNER is a category — a subset of PERSON ∪ BANK ∪ COMPANY.

How is this different from overlapping specialization?

In overlapping specialization, all subclasses inherit from one shared superclass, and an instance can belong to several subclasses at once. In a category, each member belongs to exactly one of the several unrelated superclasses at a time — a given OWNER is a person, or a bank, or a company, not several simultaneously — but which superclass applies can differ from instance to instance, and the superclasses themselves share nothing in common. The "U" precisely marks this union-of-unrelated-sets situation, distinct from both disjoint and overlapping specialization.

Quick reference: which EER construct do I need?

Chapters 8 through 11 introduced four different devices, and it's easy to blur them together once they're no longer side by side. Before moving to the full worked example, run your situation through these four questions in order — the first one that fits is the construct you want.

If you're asking...You needWorked example

The tell-tale sign you've picked the wrong one

If you find yourself inventing a superclass that doesn't correspond to anything in the requirements just so two or three subclasses have somewhere to inherit from, that's the signal to stop and check whether you actually need a category instead (Mistake 14, Chapter 13). Conversely, if you're drawing a dashed aggregation boundary around a single entity rather than around a relationship, you don't need aggregation at all — a normal relationship will do.

Chapter Twelve

Worked Example: A Full EER Diagram

The requirement, in plain English

"A hospital employs staff. Every staff member has a Staff_ID, Name, and Phone. Each staff member is either a doctor or a nurse — never both, and there is no other category of staff. Doctors additionally have a Specialization; nurses additionally have a Shift_Timing. Doctors treat patients, and for each treatment we record a Diagnosis. Patients have a Patient_ID and Name."

  • Entities: STAFF (super-entity), DOCTOR and NURSE (sub-entities), PATIENT.
  • Constraint: "either a doctor or a nurse, never both" → disjoint. "No other category" → total.
  • Relationship: DOCTOR–treats–PATIENT, one-to-many, carrying Diagnosis.

Compare this diagram against the requirement sentence by sentence. Every noun phrase should map onto something you can point to: an entity, an attribute, a relationship, or a constraint marking.

Chapter Thirteen

Mistakes Almost Every Beginner Makes

Ordered from the most common conceptual mix-up down to smaller finishing-touch errors.

Adding primary keys and foreign keys to the ER diagram

Students who've already studied SQL can't resist writing "PK" or "FK" next to attributes. There is no foreign-key notation in Chen's notation — a relationship diamond already fully captures the connection. Foreign keys only appear once the diagram is converted into tables, a later stage.

Overthinking itWriting "Dept_ID (FK)" inside the EMPLOYEE rectangle.
Correct at this stageA "belongs to" relationship diamond connecting EMPLOYEE to DEPARTMENT.

Confusing an attribute with an entity

Use the Chapter 2 test: does the "thing" need its own attributes, or could it relate to more than one instance of something else?

Too simplifiedDEPARTMENT kept as an attribute "Dept_Name" inside EMPLOYEE, even though the system also tracks department budgets and locations.
Correctly modeledDEPARTMENT promoted to its own entity with Dept_Name, Location, Budget, connected via "works in."

Confusing a relationship with an entity

If the association carries enough independent meaning to feel like a "thing" in its own right, it may need to become a full entity, often reached through aggregation (Chapter 10).

Misreading which side gets the "1" and which gets the "N"

Always sanity-check with the sentence test from Chapter 5: "One ___ can have many ___."

Forgetting participation constraints entirely

Get in the habit of asking, for every entity in every relationship: "can this exist without ever taking part here?"

Treating three related entities as a ternary relationship when two binary ones would do

A genuine ternary relationship (Figure 4.2) is needed only when the fact is inseparably about all three at once. If it can be broken into two independent binary relationships without losing information, prefer that.

Leaving a multivalued attribute as-is when it should be promoted to an entity

A double-oval multivalued attribute is valid until it needs details of its own — e.g. recording whether each phone number is "Home" or "Work" requires promoting it to its own entity.

Incomplete weak-entity representation

A weak entity needs all three parts together (Chapter 6): the double rectangle, the dashed-underline partial key, and the double-lined identifying relationship. Missing any one is a half-finished answer.

Mixing notation styles on one diagram

Don't use a Chen-style diamond in one place and a Crow's-Foot line-ending elsewhere. Pick one system and use it consistently.

Drawing redundant relationships

If a fact can already be derived by following two existing relationships, a third direct relationship expressing the same thing is usually unnecessary and risks contradictory data.

Overcomplicating the diagram with implementation detail

Data types, field lengths, indexes, and normalization belong to later design stages, not the conceptual ER diagram.

Forgetting the key attribute altogether

Without an underlined key attribute, the entity set isn't properly defined. Confirm every strong entity has at least one before considering the diagram finished.

Naming relationships vaguely ("R1", "relates to")

A relationship name should let the diagram read as a real sentence: "manages," "enrolls in," "treats."

Leaving specialization constraints unmarked

Drawing the ISA triangle without deciding disjoint/overlapping ("d"/"o", Figure 9.1's Venn diagrams) and total/partial (single/double line) leaves out exactly the information EER was invented to express.

Forcing unrelated superclasses into one specialization instead of a category

If your subclasses genuinely come from several unrelated superclasses (Chapter 11's PERSON / BANK / COMPANY example), forcing them into a shared "specialization" superclass invents a superclass that doesn't really exist. Use a category (circled U) instead.
