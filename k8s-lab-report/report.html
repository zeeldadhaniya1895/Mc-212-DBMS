Notes on the environment

The lab was done on a Linux VM, not WSL on a laptop. Two extra setup steps were needed, and they cause two small differences from the sample outputs in the manual. Everything else follows the manual exactly.

  1. containerd setting in kind-config.yaml (Figure 4). On this VM a container may not lower its OOM score. The system Pods (etcd, kube-apiserver and others) request a score of -998, so the first kind create cluster attempt failed with failed to update /proc/self/oom_score_adj: Permission denied. The setting restrict_oom_score_adj = true makes containerd limit the value instead of failing. It does not change anything the lab teaches.
  2. Images loaded into the nodes (Figure 7). The kind nodes on this VM have no direct route to Docker Hub, so the three images (nginx:stable, nginx:stable-alpine, burgxy/webapps:v4) were pulled by the host's Docker and copied in with kind load image-archive. The YAML files and image names are the same as in the manual.
  3. Effect on Step 6. Because the nodes cannot reach the registry, the describe Events for the broken Pod show a connection error instead of "not found". The cause was confirmed separately: Docker Hub returns 404 for that tag (Figure 42).
  4. Step 5 outputs. The manual makes two updates (stable-alpine, then webapps:v4), so rollout undo returned to the previous revision, nginx:stable-alpine. The manual's sample says nginx:stable. Applying the file afterwards first printed configured (it restored the file's webapps:v4) and then unchanged on the second apply. Both outputs are explained at Figures 34–35.

Observation: The cluster is gone, but kind-config.yaml, deployment.yaml, service.yaml and storage.yaml remain, so the whole lab can be rebuilt from files.

What I learned

  1. Kubernetes is a thermostat for software. I wrote down a desired state (3 copies of nginx) and controllers kept it true, for example by replacing a deleted Pod within about 2 seconds.
  2. My cluster has one control plane and two workers. The NoSchedule taint keeps application Pods off the control plane, so a bad app cannot stop me fixing things.
  3. One file produced a Deployment, a ReplicaSet and three Pods, placed on two machines I never named. created means "saved in etcd", not "running", which is why I used kubectl wait.
  4. A Service is one fixed address that finds Pods by label; kubectl get endpoints proved it matched 3 (then 5) Pods.
  5. Deleting a Pod does not delete an app; only changing the desired state does. rollout restart redeploys with no file change: Pods are replaced, never restarted (RESTARTS stayed 0).
  6. describe when it never started, logs when it started but is wrong. A failed update (ImagePullBackOff) was not an outage, and rollout undo fixed it.
  7. A PersistentVolumeClaim gives a Pod storage that outlives it: data written by one Pod was still there in its replacement.

Check yourself: answers

Q1 — You applied a Deployment with replicas: 3. Which objects exist now, and who made them?

A Deployment (written by me), one ReplicaSet (made by the Deployment controller) and three Pods (made by the ReplicaSet controller). Figure for Step 2 shows nginx → nginx-6977c7b65c → nginx-6977c7b65c-xxxxx.

Q2 — You deleted a Pod. Thirty seconds later there are still three. Why?

The desired state is still 3. The ReplicaSet controller saw 2 and created a new Pod (7gn85) with a new name and IP. To really remove the app you delete the Deployment.

Q3 — The Service says app: nginx-web but the Pods say app: nginx. What does the user see?

A connection error or timeout. The Service has zero endpoints (kubectl get endpoints shows <none>), even though every Pod is Running. The failure is silent.

Q4 — After kubectl rollout restart the Pod names changed but RESTARTS is still 0. Is that correct?

Yes. The old Pods were deleted and new ones created one at a time (hash 86989cccf7 → 7c78f7b556). A restart in place would keep the name and set RESTARTS to 1.

Q5 — A new Pod is in ImagePullBackOff. Why do users still get a working site, and how do you recover?

The rolling update waits for new Pods to become ready before removing old ones, and the Service never adds the broken Pod. The 3 old Pods kept serving. Recover with kubectl rollout undo deployment/nginx.
